# BranchLab: Interactive Branch Prediction Simulator

BranchLab is a Computer Organization and Architecture (COA) project. It is a browser-based simulator for **1-bit** and **2-bit saturating-counter** branch predictors. You enter a sequence of branch outcomes, step through it one branch at a time, and inspect every prediction, state update, misprediction and estimated pipeline cost. Both predictors can be compared on the same input.

Everything is computed in the browser by the simulation code. Nothing is hard-coded, and no backend, account or network connection is needed.

## Objectives

- Implement genuine 1-bit and 2-bit predictors with an independent entry per branch address.
- Let users build, validate and run their own branch-outcome sequences, step by step or all at once.
- Measure accuracy and mispredictions, and estimate penalty cycles, total cycles and CPI under a documented pipeline model.
- Compare the two predictors on identical inputs and explain the measured difference.
- Visualise the state machines and a pipeline flush caused by a misprediction.

## Features

- **Simulator**: an input editor with live validation; Step Forward, Run / Re-run Simulation, Reset, Load Example and Clear Input; configurable initial states.
- **Execution trace**: step, branch, actual outcome, prediction, CORRECT/MISPREDICT label, state before and after, and cumulative mispredictions.
- **Metrics**: accuracy, misprediction rate, penalty cycles, base cycles, estimated cycles and CPI, each shown with its formula and the values substituted in.
- **State diagrams**: the 1-bit and 2-bit diagrams highlight the selected branch's current state and its most recent transition.
- **Predictor table**: one entry per branch address, so you can see that states are independent.
- **Comparison mode**: a side-by-side table, bar charts and a deterministic written analysis, all computed from the measured numbers.
- **Pipeline view**: a cycle-by-cycle timing diagram for any trace step, with wrong-path instructions shown being flushed after a misprediction.
- **Built-in experiments**:

  | | Experiment | Sequence |
  |---|---|---|
  | A | Loop-like branch | `T T T T T T T N` |
  | B | Alternating | `T N T N T N T N` |
  | C | Mostly NOT TAKEN | `N N N N T N N N` |
  | D | Independent addresses | `B1:T B2:N …` |
  | E | Custom | your own sequence |
  | F | Loop executed repeatedly | `T T T N` × 3 |

- **Learn page**: concise theory, including a worked example generated by the simulator.
- **About page**: project summary and a suggested order for a live demonstration.

## Input format

```
T N T T N          outcomes of one branch (address B0)
B1:T B2:N B1:N     outcomes of several branches
0x40A0:T loop:N    hex or name addresses
```

- `T` means TAKEN and `N` means NOT TAKEN. Tokens are separated by spaces, commas, semicolons or new lines.
- Case does not matter, and addresses are normalised to upper case.
- Invalid entries are reported with their position and an explanation.

## How the 1-bit predictor works

Each branch address has one bit. A bit of `1` predicts TAKEN and `0` predicts NOT TAKEN. After the branch resolves, the bit is set to the actual outcome. A single unusual outcome therefore flips the next prediction. For example, a loop exit costs two mispredictions: the exit itself and the first iteration the next time the loop runs.

## How the 2-bit predictor works

Each branch address has a saturating counter:

| Counter | State | Prediction |
|---|---|---|
| `00` | Strongly Not Taken | NOT TAKEN |
| `01` | Weakly Not Taken | NOT TAKEN |
| `10` | Weakly Taken | TAKEN |
| `11` | Strongly Taken | TAKEN |

- The prediction is read from the **old** counter value.
- An actual TAKEN outcome increments the counter, saturating at `11`.
- An actual NOT TAKEN outcome decrements it, saturating at `00`.

From a strong state it takes two consecutive wrong outcomes to change the prediction. This usually helps with occasional anomalies, but not always. For `T T N N T T N N`, the 2-bit predictor starting at `01` makes 6 mispredictions, while the 1-bit predictor starting at `0` makes 4. This case is covered by a unit test.

## Formulas

| Quantity | Formula |
|---|---|
| Accuracy | `correct / branches processed × 100` |
| Misprediction rate | `mispredictions / branches processed × 100` |
| Penalty cycles | `M × P` |
| Estimated cycles | `I + (L − 1) + M × P` |
| CPI | `estimated cycles / I` |

The symbols are:

- `I`: total dynamic instruction count (configurable; must be at least the number of branches)
- `L`: pipeline depth
- `M`: number of mispredictions
- `P`: penalty per misprediction in cycles

The defaults are `I = 40`, `L = 5` and `P = 2`.

## Assumptions and limitations

- The cycle model describes an ideal pipeline (one instruction per cycle after L − 1 fill cycles) plus a fixed P-cycle penalty per misprediction. It ignores data and structural hazards, cache misses, branch-target-buffer misses and overlapping stalls. Cycle and CPI figures are **estimates under this model**, not hardware measurements.
- Instructions that are not in the branch sequence (`I` minus the number of branches) are assumed never to stall.
- During step-by-step execution, the cycle estimate includes only the mispredictions resolved so far. The interface labels these as partial results.
- Every branch address gets its own predictor entry. There is no finite table, so there is no aliasing, and no branch target buffer is modelled.
- The pipeline diagram assumes that a branch resolves `P` cycles after fetch, in stage `P + 1`. It can only be drawn when `P ≤ L − 1`. The metrics use any valid `P`.
- Real processors resolve branches in different stages, use far more sophisticated predictors, and have different penalties. BranchLab does not model any specific processor.

## Getting started

You need Node.js 18 or newer and npm.

```bash
npm install
```

```bash
npm run dev
```

Then open the URL that Vite prints (usually http://localhost:5173).

Other commands:

```bash
npm test
```

```bash
npm run build
```

```bash
npm run preview
```

- `npm test` runs the unit tests once. Use `npm run test:watch` to re-run them on every change.
- `npm run build` type-checks the project and writes a production build to `dist/`.
- `npm run preview` serves that production build locally.

`npm run build` produces **one self-contained file**, `dist/index.html`, with JavaScript, CSS and fonts inlined. A copy is kept as `BranchLab.html` in the project root.

## Live site and deployment

The site is hosted on GitHub Pages from the `gh-pages` branch. To publish a new version after changing the code:

```bash
npm run deploy
```

This rebuilds the project and pushes `dist/index.html` to the `gh-pages` branch of the `origin` remote.

`BranchLab.html` (a copy of the build) can also be submitted on its own: it opens by double-clicking in Chrome, Edge or Firefox, with no server or internet connection.

## Tests

There are 72 unit tests. They cover every required case:

- 1-bit updates after TAKEN and after NOT TAKEN
- state reuse for the same address
- independent states for different addresses
- 2-bit increment, decrement and saturation at `11` and `00`
- prediction made before the update
- accuracy and penalty calculations
- step-by-step, partial and full runs giving identical results
- reset
- rejection of invalid input with readable messages
- identical input to both predictors in comparison mode
- no state carried over when a sequence is re-run

They also cover cycle-model validation, the session's edit and restart rules, the comparison analysis, and the pipeline timing model.

## A short explanation for the demonstration

> A pipelined processor has to fetch the next instruction before a branch has been resolved, so it predicts the direction. BranchLab simulates two classic dynamic predictors.
>
> The 1-bit predictor remembers each branch's last outcome. The 2-bit predictor keeps a saturating counter, so one unusual outcome only weakens its prediction instead of flipping it.
>
> As we step through a sequence, the trace shows, for every branch, the prediction made from the old state, whether it was correct, and how the state was updated. The diagram highlights the same transition.
>
> Every misprediction flushes the wrong-path instructions and costs P cycles. The metrics show how this raises total cycles and CPI under a simple pipeline model.
>
> Comparing the predictors on a repeated loop shows the 2-bit counter avoiding the 1-bit predictor's double misprediction at each loop exit. Other patterns show that it is not always better: accuracy depends on the workload and the initial state.
